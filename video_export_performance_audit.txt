VIDEO EXPORT PERFORMANCE AUDIT - ScreenRec (Android, Kotlin)
=================================================================

PROJECT CONTEXT
----------------
- App: Android screen recorder + video editor ("ScreenRec"), package com.nkd.screenrecorder.
- Editing pipeline is implemented with FFmpegKit (com.moizhassan.ffmpeg:ffmpeg-kit-16kb:6.1.1,
  declared in gradle/libs.versions.toml and app/build.gradle.kts). No Media3 Transformer, no raw
  MediaCodec/MediaMuxer usage anywhere in the app (verified by grep - zero matches for
  androidx.media3, Transformer, EditedMediaItem).
- Default screen-recording frame rate is 30 fps (RecordScreenService.kt:73, frameRate = 30).
- Problem: exporting a video after multiple edits (trim, crop, text, stickers, music/volume) is
  too slow. Single-edit exports are comparatively fine.

Every FFmpegKit.execute*Async call in this chain is a SEPARATE, full, sequential
decode -> filter -> encode pass over the entire video, each reading the previous step's
full-length MP4 from disk and writing a brand-new full-length MP4 to disk.

3. CURRENT EXPORT ARCHITECTURE
--------------------------------
Source video (content:// or cache file)
 -> FFmpeg pass #1  (trim)         -c:v libopenh264, -vf fps=60               -> Trim_<ts>.mp4
 -> FFmpeg pass #2  (crop)          -c:v libopenh264, -vf fps=60,crop,scale    -> cropped_<ts>.mp4
 -> FFmpeg pass #3  (plain text)    -c:v libopenh264, -vf fps=60,drawtext*N    -> text_overlay_<ts>.mp4
 -> FFmpeg pass #4  (labeled text)  -c:v libopenh264, filter_complex overlay*N -> sticker_overlay_<ts>.mp4
 -> FFmpeg pass #5  (stickers)      -c:v libopenh264, filter_complex overlay*N -> sticker_overlay_<ts>.mp4
 -> FFmpeg pass #6  (music/volume)  -c:v copy, amix / volume filter           -> music_overlay_<ts>.mp4
 -> File copy (exportFinalToOutput) plain byte copy into SAF output file
Final MP4

Up to 5 full video re-encodes (passes 1-5; pass 6 is audio-only, -c:v copy) can run in one
export if trim + crop + plain text + labeled text + stickers are all present. Each pass is
gated only by "is this edit type present" - nothing merges filters across passes.

4. MAIN PERFORMANCE BOTTLENECK
--------------------------------
Sequential, per-edit-type full video re-encoding, compounded by:
1. A fixed -vf fps=60 baked into every video-touching pass, even though the recorder
   defaults to 30 fps - doubling frame count processed by every pass.
2. The encoder is ALWAYS software (libopenh264) - hardware is never used.
3. Every pass re-probes MediaMetadataRetriever for bitrate from scratch and fully
   re-decodes just to re-encode.
4. Every pass writes a new full-resolution MP4 to app storage; none are deleted on a
   SUCCESSFUL export (only on manual cancel - see section 9).

Notes:
- libopenh264 (Cisco's software H.264 encoder) is used in every video pass - no hardware
  route exists in an FFmpegKit-based pipeline the way it would with native MediaCodec or
  Media3 Transformer.
- fps=60 is hard-coded into every video filter regardless of source fps (default 30) -
  silently doubles frame-processing cost on every pass.
- No -preset/-g/-profile/-level tuning anywhere - encoder defaults used.
- Bitrate/metadata re-probed via a fresh MediaMetadataRetriever in every single step
  instead of computed once.
- All filters (trim/crop/drawtext/overlay) are consolidatable into one -filter_complex.

9. TEMP FILE / DISK I/O AUDIT
-------------------------------
Worst case (trim + crop + plain text + labeled text + stickers + music/volume all present)
writes up to 6 full-size intermediate MP4s:
- getExternalFilesDir(MOVIES)/trim/Trim_<ts>.mp4
- getExternalFilesDir(MOVIES)/cropped/cropped_<ts>.mp4
- getExternalFilesDir(MOVIES)/textOverlay/text_overlay_<ts>.mp4
- getExternalFilesDir(MOVIES)/stickerOverlay/sticker_overlay_<ts>.mp4  x2 (labeled text + stickers)
- getExternalFilesDir(MOVIES)/music/music_overlay_<ts>.mp4 or volume_<ts>.mp4
- plus per-track music file copies (content:// -> cacheDir) and a full crop_input_<ts>.mp4
  copy when source is content://.

CONFIRMED LEAK: exportIntermediates (EditVideoActivity.kt:6352) is populated on every pass
start (rememberExportIntermediate(), line 6398) but is only drained/deleted inside
stopExport() (lines 6451-6452), which runs ONLY on manual cancel. The success path
(saveAllPendingEdits() completion -> clearEditStateCache(), line 3096, which only removes a
draft DB row) never deletes these files. EVERY SUCCESSFUL EXPORT PERMANENTLY LEAVES BEHIND
EVERY INTERMEDIATE MP4 IT PRODUCED. This is a genuine storage leak, not just an efficiency
note.

All copying/writing is plain stream-based disk I/O - no pipes, no streaming between
passes; everything round-trips through disk.

10. THREADING / CONCURRENCY AUDIT
------------------------------------
- FFmpegKit.executeAsync/executeWithArgumentsAsync run off the main thread; all callbacks
  are explicitly wrapped in runOnUiThread { ... } - no evidence of encode work blocking
  the UI thread.
- exportFinalToOutput()'s SAF file copy (EditVideoActivity.kt:5566-5568) and
  VideoCropper's content:// -> temp-file copy (VideoCropper.kt:48-49) are synchronous
  stream copies with NO coroutine/Dispatchers.IO offload. exportFinalToOutput is invoked
  from inside a runOnUiThread block (line 6503), meaning THIS FILE COPY RUNS ON THE MAIN
  THREAD - a real, confirmed (if secondary) main-thread I/O call that can cause jank on
  large files.
- No simultaneous/duplicate FFmpeg sessions - the chain is strictly sequential via nested
  callbacks, gated by isExportActive.

11. DUPLICATE EXPORT AUDIT
-----------------------------
- Only one listener reaches saveAllPendingEdits() (confirmed by grep).
- saveAllPendingEdits() (line 6455) has NO reentrancy guard (no "if (isExportActive)
  return" at the top). A rapid double-tap on Save before the full-screen export overlay
  appears could theoretically start a second chain. Not confirmed exploitable in
  practice, but confirmed absent in code.

12. PERFORMANCE ANTI-PATTERNS (ranked)
-----------------------------------------
P0 - Critical
- Up to 5 sequential full video decode+encode passes instead of 1 (saveAllPendingEdits /
  burnTrimStep / burnCropStep / burnTextStep / burnStickerStep in EditVideoActivity.kt;
  burn / burnAllStickers in VideoTextBurner.kt; crop in VideoCropper.kt).
- fps=60 hard-coded into every video filter despite a 30fps-default source
  (VideoTextBurner.kt:113,346,424; VideoCropper.kt:115).

P1 - High
- Software-only encoding (libopenh264) everywhere - no hardware path in the current
  architecture.
- Successful-export intermediate files never deleted (EditVideoActivity.kt:6352,6398 vs.
  6451-6452 only firing in stopExport).
- Bitrate/metadata re-probed from scratch on every pass (VideoTextBurner.kt:46;
  VideoCropper.kt:210).

P2 - Medium
- Synchronous main-thread file copies in exportFinalToOutput and VideoCropper.crop's
  content-URI staging.
- No reentrancy guard in saveAllPendingEdits().

P3 - Low
- No GOP/profile/level/preset tuning (unverified impact).

15. RECOMMENDED OPTIMIZATION
-------------------------------
1. Collapse the 5-stage video chain into one FFmpeg invocation. Build a single
   -filter_complex in EditVideoActivity: trim via -ss/-t (or in-graph trim= if
   frame-accurate sync with overlays is needed), crop via crop=, each text overlay via
   drawtext=, each sticker/label via scale=+overlay= - all chained, with one
   "-c:v libopenh264 -b:v <bitrate>", one "-c:a aac", one output. This is where almost
   all the time savings come from.
2. Drop the hard-coded fps=60. Only add fps= if the user explicitly requests a
   frame-rate change.
3. Compute bitrate/metadata once at export start, thread it through the single combined
   command.
4. Fix the intermediate-file leak - delete exportIntermediates (minus final output)
   after successful exportFinalToOutput(), mirroring stopExport().
5. Move the final SAF file copy off the main thread.

Second-tier, higher-risk option: migrate video-affecting operations off FFmpegKit onto
native MediaCodec/MediaMuxer or Media3 Transformer for real hardware-accelerated
encoding - pursue only after single-pass consolidation is in place and measured.

16. EXPECTED PERFORMANCE IMPROVEMENT
---------------------------------------
Architecture-derived estimates (not yet measured):
- 1 edit type active (e.g. crop only): ~10-20% (mostly from removing forced fps doubling).
- 2-3 edit types active (trim + crop + text - common case): roughly 2-3x faster.
- 4-5 edit types active (trim + crop + text + labeled text + stickers): roughly 4-5x faster.
Removing forced fps=60 alone should cut per-pass work by close to half for 30fps-sourced
recordings, compounding with the pass-count reduction. Validate with before/after timing
instrumentation (log points: EXPORT_START, per-pass start/end, ENCODE_END, MUX_END,
EXPORT_COMPLETE).

17. RISK / REGRESSION ANALYSIS
---------------------------------
- Video quality: should be unaffected or improved (fewer re-encode generations = less
  cumulative lossy-compression loss).
- Audio sync: highest risk - today trim runs as its own isolated pass before overlay
  timing is baked in, so overlay start/end times are already expressed in
  trimmed-timeline terms. When trim becomes -ss/-t on the same combined command, verify
  whether drawtext/overlay enable='between(t,...)' expressions still line up (FFmpeg's
  -ss placement before/after -i changes whether downstream filter t is pre- or
  post-trim) - needs explicit testing.
- Crop: crop coordinates are computed against the pre-crop frame; in a combined graph,
  overlay x/y must be recomputed relative to the cropped frame, and crop must precede
  overlay/drawtext in filter order.
- Rotation: no rotation-burning code found in this flow - out of scope, but if added
  later it must also join the combined graph rather than becoming a 6th pass.
- Filters/overlays/watermark: existing per-type models already produce filter-fragment
  strings; consolidation is mostly concatenating fragments correctly, not a data-model
  redesign.
- Subtitles: not present in this codebase's edit model.
- Output compatibility: unchanged (same codec/container) unless the hardware-encoder
  migration is later pursued.
- Android versions: no version-specific risk from filter-graph consolidation; existing
  SAF/content:// handling (resolveFfmpegInputPath) is untouched.
